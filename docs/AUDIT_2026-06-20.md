## 1. Zusammenfassung

Meridian ist auf einem **guten Weg** bei der Design-Zentralisierung. Die
fundamentale Architektur steht:

- `meridian-config` (`ThemeConfig`/`Decorations`) ist die Single Source für
  Geometrie, Radii, Schatten und Glas-Behandlung.
- `meridian-tokens` liefert `Palette`, `Radius`, `Elevation`, `Interaction`
  (Zustands-Token für hover/pressed/accent-cushion).
- Theme-Dateien (`themes/dark`, `themes/light`) enthalten **nur** `[colors]`
  plus Icons/Wallpaper – alle Glas-/Geometriewerte kommen aus zentralen
  Rust-Defaults.
- `surface_treatment(ThemeSurface)` liefert *einen* einheitlichen Satz
  Fill/Frame/Blur/Tint für Panel/Launcher/Popup/Modal/Control – nur die Radii
  differenzieren.
- Der Compositor reicht `fill_alpha` konsistent durch `GlassTitlebarInfo`
  weiter (alter Kritikpunkt aus 2026-05-25: **behoben**).
- Login, Lock und Polkit sind an `meridian_config::ThemeConfig` angebunden.

**Aber:** Es gibt noch **neun Stellen**, an denen GUI-Elemente ihre eigene Suppe
kochen. Diese sind in §3 priorisiert dokumentiert – dort liegt der Hebel für
dein Ziel, dass *alles identisch aussieht*.

## 2. Architektur-IST-Stand (Design-Pfade)

### 2.1 Die Single Sources

```
meridian-tokens   ──► kanonische Palette (DARK/LIGHT), Radius, Elevation,
                      Interaction (hover/pressed/accent-cushion)
        ▲
        │ (Defaults werden gespiegelt, nicht kopiert)
        │
meridian-config   ──► ThemeConfig { colors, decorations, fonts, icons, … }
                      └── Decorations::default()  ← EINE Geometrie-/Glasquelle
                          ├── surface_radius(ThemeSurface) → f32
                          └── surface_treatment(ThemeSurface) → SurfaceTreatment

                                fill_alpha, frame_alpha }
```

`themes/dark/theme.toml` und `themes/light/theme.toml` enthalten **ausschließlich**
`[colors]`, `[icons]`, `[wallpaper]`. Keine `[decorations]`-Sektion – die
kommen aus `Decorations::default()`. ✅ Das Modell entspricht exakt deiner
Vorgabe.

## 3. Design-Zentralität: Befund (Hauptaugenmerk)

Dies ist der Kern deines Auftrags. Alle Funde sind priorisiert und mit
Lokation + Vorschlag versehen, damit du sie nacheinander abarbeiten kannst.

### 3.1 HOCH – `panel_view.rs` (Kompass-Icon) – eigene Farbpalette

**Lokation:** `crates/meridian-shell/src/panel_view.rs`

**Befund:** Das Kompass-Element malt mit hartcodierten `paint_rgba`-Werten, die
nichts mit `theme.colors` zu tun haben:

```rust
&paint_rgba(0, 0, 0, 92),            // Schatten
&paint_rgba(18, 22, 34, 255),        // Body-Fill (hartes Dunkelblau)
&paint_rgba(255, 255, 255, 36),      // Specular-Highlight
&paint_rgba(0, 0, 0, 42),            //??? zweite Schattenart
&paint_rgba(0, 0, 0, 66),            //??? dritte
&paint_rgba(246, 249, 255, 255),     // Text/Fordergrund (hartes Weiß)
&paint_rgba(18, 22, 34, 230),        //??? Variante des Body
&paint_rgba(255, 255, 255, 210),     //??? Variante des Highlights
```

Dazu: `.lerp(Color::rgb(0xFF, 0xFF, 0xFF), 0.15)` (hart, nicht
`Interaction::hover`).

**Warum das falsch ist:** Das Kompass-Element tauscht bei Theme-Wechsel nicht
die Farben – es bleibt dunkelblau, auch im Light-Theme. Genau das
"jedes-Element-seine-eigene-Suppe"-Problem, das du ansprichst.

**Vorschlag:**
- RGB-Komponenten durch `theme.colors.{background,surface,surface_alt,text,text_dim,border}` ersetzen.
- Alpha-Werte (92/36/42/66/210) in `meridian-tokens` als benannte Konstanten
  oder – besser – als Teil eines `CompassStyle`-Structs in `meridian-compass-render`, das aus `ThemeConfig` abgeleitet wird.
- Schatten über `Elevation::LAUNCHER` (wie `meridian-login` es schon macht).

---

### 3.2 HOCH – `settings_view.rs` – hardcoded Aufhellungen

**Lokation:** `crates/meridian-shell/src/settings_view.rs`

**Befund:** Drei Stellen hellen eine Surface künstlich auf weiß auf, statt das
Theme zu nutzen:

```rust
.surface.lerp(Color::rgb(0xFF, 0xFF, 0xFF), 0.08)   // 3× identisch
```

Zusätzlich: `self.accent.lerp(Color::rgb(0, 0, 0), 0.55)` für ein Icon.

**Warum das falsch ist:** `Interaction::hover` macht genau das
(`base.lerp(WHITE, hover_lighten)`), aber mit dem zentralen Wert `0.10`. Hier
wird `0.08` hardcoded – minimal anders, aber **inkonsistent** mit jedem Widget,
das `Interaction` nutzt. Im Light-Theme ist `0xff,0xff,0xff` zudem die falsche
Richtung (Surface ist dort schon hell, "Aufhellung" macht nichts sichtbar).

**Vorschlag:** Statt `.lerp(WHITE, 0.08)` entweder
`Interaction::DEFAULT.hover(theme.palette.surface)` verwenden oder – falls es
ein "selected/focused"-Zustand ist – einen neuen Token `Interaction::selected`
einführen und die drei Stellen darauf umleiten.

---

### 3.3 HOCH – `settings_view.rs` – verstreute Accent-Lerps

**Lokation:** `crates/meridian-shell/src/settings_view.rs`

**Befund:** Für selected/focused/active/expanded-Zustände stehen fünf
verschiedene Lerp-Faktoren herum:

```rust
base.lerp(self.accent, 0.16)                          // WidgetState::Idle selected
theme.palette.surface.lerp(self.accent, 0.08)         // focused preview
theme.palette.surface_alt.lerp(self.accent, 0.10)     // expanded control
theme.palette.surface_alt.lerp(self.accent, 0.14)     // selected control
theme.palette.surface_alt.lerp(self.accent, 0.12)     // active control
```

**Warum das falsch ist:** `Interaction` hat bereits `accent_idle_alpha` (54)
und `accent_hover_alpha` (80) als *transluzenten Accent-Cushion* – die
*korrekte* Methode für "active/selected über Glas". Die Lerp-Variante ist
opak, verhält sich in Dunkel-/Hell-Theme unterschiedlich und ist fünfmal
subtil anders.

**Vorschlag:**
- Einen Token-Begriff "selection cushion" einführen: `Interaction::selection(base, accent)` – *eine* Formel.
- Alle fünf Vorkommen auf diesen einen Helfer umstellen.
- Das `0.16`-Vorkommen ist vermutlich ein Hover-Cushion → `accent_hover`.

### 3.4 MITTEL – `tokens.rs` – hardcoded Kontrastfarben

**Lokation:** `crates/meridian-shell/src/ui/tokens.rs:32-34`

**Befund:**

```rust
pub(crate) fn accent_foreground_from_config(config: &ThemeConfig) -> Color {
    let accent = config.colors.accent;
    let lum = 0.299 * accent.r as f32 + 0.587 * accent.g as f32 + 0.114 * accent.b as f32;
    if lum > 150.0 {
        Color::rgb(0x05, 0x08, 0x0c)        // ← hardcoded "fast schwarz"
    } else {
        Color::rgb(0xf6, 0xf9, 0xff)        // ← hardcoded "fast weiß"
    }
}
```

**Warum das ein Lücken-Fund ist:** Die Berechnungsmethode (Luminanz-Schwellwert
150) ist *doppelt* im Codebase: `ThemeConfig::appearance_is_light()` nutzt die
gleiche Formel mit Schwellwert 140. Und die zwei Resultatfarben sind "Magic
Values", die nirgendwo als Theme-Werte auftauchen.

**Vorschlag:**
- Schwellwert und Formel zentralisieren (`meridian-tokens` als `relative_luminance(color)` + `is_light(color)`).
- Die zwei Kontrastfarben als `Palette::TEXT_ON_LIGHT`/`TEXT_ON_DARK` ins Token-Modul – dann sind sie wenigstens *benannt* und an einem Ort.

### 3.5 MITTEL – `app_view.rs` – lokale Launcher-Alpha-Konstanten

**Lokation:** `crates/meridian-shell/src/app_view.rs`

**Befund:** Neun lokal gebündelte Konstanten für den Launcher:

```rust
const LAUNCHER_BAND_ALPHA: u8 = 0;
const LAUNCHER_CELL_ALPHA: u8 = 0;
const LAUNCHER_HOVER_ALPHA: u8 = 42;
const LAUNCHER_SELECTED_ALPHA: u8 = 56;
const LAUNCHER_TILE_RADIUS: i32 = meridian_tokens::Radius::DEFAULT.md;  // ✅ gut
const LAUNCHER_SEARCH_FIELD_ALPHA: u8 = 24;
const LAUNCHER_BENTO_ACCENT_ALPHA: u8 = 105;
const LAUNCHER_POWER_ARMED_ALPHA: u8 = 46;
const LAUNCHER_SCROLLBAR_TRACK_ALPHA: u8 = 25;
const LAUNCHER_SCROLLBAR_THUMB_ALPHA: u8 = 180;
const LAUNCHER_DIVIDER_ALPHA: u8 = 44;
```

**Befund nuanciert:** Die Konstanten sind *wenigstens* gebündelt und
dokumentiert ("route through `Interaction`/`surface_treatment`"), und
`LAUNCHER_TILE_RADIUS` zieht sich bereits aus `meridian_tokens`. Aber die
Alpha-Werte sind *nicht* aus `Decorations`/`Interaction` abgeleitet – sie sind
Magiezahlen, die nur hier leben.

**Warum das Relevant ist:** Wenn du global den "Selected-Look" ändern willst,
musst du `LAUNCHER_SELECTED_ALPHA`, das `0.14` in `settings_view` und das
`accent_idle_alpha` in `Interaction` *drei Orte* pflegen.

**Vorschlag:**
- `LAUNCHER_HOVER_ALPHA`/`SELECTED_ALPHA` → `Interaction::neutral_hover.a`/`accent_idle_alpha`.
- `LAUNCHER_DIVIDER_ALPHA` → neuer Token `Divider::default_alpha` in `meridian-tokens`.
- `LAUNCHER_SCROLLBAR_*` → neuer Token-Block `Scrollbar { track_alpha, thumb_alpha }`.

### 3.6 MITTEL – `login/visual.rs` – hardcoded Input-Box-Farbe

**Lokation:** `crates/meridian-login/src/visual.rs` (via Search gefunden)

**Befund:**

```rust
let box_fill = Color::from_rgba8(12, 17, 23, alpha_byte(alpha, 176.0));
```

`(12, 17, 23)` ist hardcodedes Dunkelblau, das *nicht* aus `login_theme().colors`
kommt – obwohl der Rest der Datei bereits `metro_*`-Helfer nutzt.

**Warum das falsch ist:** Im Light-Theme bleibt die Input-Box dunkelblau –
Genau das "jedes-Element-seine-Suppe"-Problem.

**Vorschlag:**
- `metro_background(alpha)` oder `metro_surface(alpha)` verwenden (beide existieren schon).
- Alpha 176 → `modal_fill_alpha(0.69)` o.ä. – die Helfer sind schon da.

### 3.7 MITTEL – `login/main.rs` – verstreute metro-Skalierungsfaktoren

**Lokation:** `crates/meridian-login/src/main.rs`

**Befund:** Die `metro_*`-Helfer sind gut (ziehen aus `login_theme()`), aber
an Aufrufstellen stehen Magic-Number-Skalen:

```rust
metro_surface(alpha)                  // modal_fill_alpha(0.75) – ✅ sauber
metro_background(alpha)               // modal_fill_alpha(0.55) – ✅ sauber
// aber an Call-Sites:
mix_color(metro_surface(1.0), metro_text_dim(1.0), 0.22)              // ← 0.22 magic
color_with_alpha(metro_success(1.0), alpha_byte(alpha, 160.0))        // ← 160 magic
color_with_alpha(metro_accent(1.0), alpha_byte(alpha, 160.0))         // ← 160 magic
```

**Warum suboptimal:** Die `0.22`/`160` sind lokal vereinbart, aber nicht
benannt. Sie *wiederholen sich* – das ist ein Kandidat für einen Token.

**Vorschlag:**
- `0.22` → `meridian-tokens::MIX_RECESSED_SLOT` (oder ähnlich, benannt).
- `160` → das ist 0.63 als Byte – sehr nah an `Interaction::accent_hover_alpha` (80/255 = 0.31). Prüfen, ob das zusammengeführt werden kann.

## 7. Offene Risiken / Annahmen

- Der Bericht basiert auf Code-Lektüre ohne Laufzeit-Verifikation. Die
  *visuelle* Wirkung der Theme-Anbindung muss nach jeder Änderung manuell
  geprüft werden (Dark- und Light-Theme, sowie Login/Lock/Polkit).
- Die `metro_*`-Helfer im Login sind ein lokales "Dialekt"-System. Sie sind
  *themefähig*, aber nicht identisch mit dem `Interaction`/`Theme`-Modell der
  Shell. Mittelfristig könnte man sie zusammenführen – das wäre aber ein
  größerer Refactor und nicht zwingend, solange beide aus derselben
  `ThemeConfig` lesen.
- Keine Aussage über Build-Status (`cargo check/test`) – siehe §5.1.
